# RadixDB

[English](README.md)

[Официальный сайт](https://radixdb.org) · [Поддержка](mailto:dev@radixdb.org)

RadixDB — открытая SQL-база данных на Rust. Она сочетает транзакционное
изменение строк со сжатым колонночным хранением, позволяя прикладным системам
экономно хранить данные и выполнять аналитические запросы.

RadixDB работает как самостоятельный TCP-сервер и как встраиваемая библиотека
Rust. Основные приоритеты движка — надёжное восстановление, управляемое
потребление памяти и эффективная работа с большими связанными наборами данных.

Разработку RadixDB спонсирует компания [Light Soft](http://light-soft.info/).

## Быстродействие и доступность

### Производительность запросов

Сравнительный тест на Ryzen 9 7950X и NVMe с реляционным набором
из 100 млн строк показал следующие задержки:

| Запрос | RadixDB | PostgreSQL 18.3 |
| --- | ---: | ---: |
| Полное сканирование | 100,299 мс | 246,457 мс |
| Чтение выбранных колонок | 23,189 мс | 84,456 мс |
| Группировка с HAVING | 9,907 мс | 24,948 мс |

В этих сценариях RadixDB работала примерно в 2,5–3,6 раза быстрее.
В том же сравнении PostgreSQL быстрее выполняла точечный и диапазонный поиск,
соединение с родительской таблицей, массовую загрузку и построение индексов.
Результаты относятся к конкретной нагрузке и зафиксированным версиям;
это не замеры каждого последующего коммита.
[Полный отчёт и методика](doc/src/content/docs/ru/appendices/benchmarks.md) показывают
как преимущества, так и более медленные сценарии.

### Надёжность в сложных условиях

Транзакции, журнал предзаписи, контрольные суммы и проверяемые физические
снимки обеспечивают основу восстановления. В шестичасовом испытании база
из 100 млн строк обслуживала до 256 клиентов на машине с 1,76 ГиБ ОЗУ
и жёстким диском на 5400 об/мин.

Во время испытания реальный сбой связи SATA прервал операцию сброса данных
на диск. Ядро восстановило соединение и повторило операцию, после чего движок
продолжил работу. Прогон завершил 2 351 035 операций и 2 100 проверок
инвариантов без их нарушений; логическая контрольная сумма восстановленного
снимка совпала с исходной базой. Этот результат подтверждает восстановление
после наблюдавшегося временного сбоя. Он не означает защиту от окончательной
утраты диска. В отчёте также отражены временные остановки прогресса и выход из них.

### Низкое потребление памяти

Для работы с большой базой не требуется целиком загружать её в память процесса.
В том же испытании на 100 млн строк пиковая резидентная память сервера
составила около 1 011 МиБ, а после завершения нагрузки снизилась до 197 МиБ.

Для небольших устройств профиль на 20 000 строк и 120 таблиц показал
23,4 МиБ после повторного открытия базы с системным аллокатором и 54,2 МиБ
с используемым по умолчанию mimalloc. Это результаты отдельных профилей
с явно заданными настройками рабочих потоков и кэша.

### Основа на Rust

Общая реализация на Rust используется во встраиваемой библиотеке и TCP-сервере
и не требует управляемой среды исполнения. Rust создаёт основу для переноса
движка между процессорными архитектурами и операционными системами.
Приведённые результаты получены на Linux x86-64; другие платформы требуют
отдельной проверки сборки, файловых операций и восстановления.

Приложения могут использовать библиотеку `radixdb`, самостоятельный
TCP-клиент `radixdb-client` и слой доступа к данным `radixdb-orm`.

## Особенности движка и функциональность

### Гибридное хранение связанных данных

Изменяемые строки с MVCC сочетаются с неизменяемыми сжатыми блоками колонок,
объединёнными в группы строк. Такая гибридная строчно-колонночная организация
поддерживает транзакционные изменения и позволяет при сканировании читать
нужные запросу колонки. Статистика блоков помогает отбрасывать неподходящие
группы строк до чтения их содержимого.

Это полезно для широких связанных наборов данных, где обновления соседствуют
с фильтрацией и агрегацией: реестров объектов, телеметрии, атрибутивных данных
геоинформационных систем. Геобазы могут использовать эти способы доступа
к атрибутам; геометрические типы, пространственные индексы и GIS-функции
поставляются отдельным native extension и не следуют из устройства хранилища.

### Компактное хранение и настраиваемый кэш

Неизменяемые файлы данных содержат сжатые блоки колонок. В сравнительном
испытании сентября 2026 года база из 100 млн строк занимала 1,96 ГБ
логического объёма против 16,13 ГБ у PostgreSQL: примерно в 8,2 раза меньше
на этом наборе данных.

Сжатие позволяет разместить в памяти больше данных. RadixDB предоставляет
bounded materialized volume cache и дополнительный прогрев файлового кэша ОС.
Если сжатая база помещается в доступный бюджет памяти, в page cache может
находиться большая часть или весь объём её файлов, сокращая повторные обращения
к диску. Фактическое размещение зависит от свободной памяти и нагрузки; ОС
может вытеснять страницы.

В конфигурации сервера доступны `page_cache_level`, `page_cache_max_bytes` и
`page_cache_memory_reserve`. Прежние placeholders `block_cache_bytes` и
`scan_prefetch_cache_bytes` удалены и строго отклоняются; embedded file DSN
отдельно поддерживает реальный `volume_cache_bytes`.
Подробнее — в [описании кэша и границ памяти](doc/src/content/docs/ru/administration/memory.md).

### Навигационные ссылки

RadixDB позволяет обращаться к связанным данным прямо в SQL через путь по
внешнему ключу. Связь становится частью выражения: для чтения атрибутов
связанной записи не нужно каждый раз повторять условия JOIN.

```sql
CREATE TABLE departments (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE employees (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    department_id INTEGER REFERENCES departments(id)
);

SELECT e.name, e.department_id.name AS department
FROM employees AS e;
```

При корректных внешних ключах результат совпадает с LEFT JOIN сотрудников
и отделов. Если ссылка на отдел равна NULL, название отдела тоже будет NULL.
В самой строке сотрудника по-прежнему хранится обычное значение ключа.

Путь может проходить через несколько связей, например
`p.employee_id.department_id.name`. Обращения к разным полям по одному пути
используют общие переходы. Движок определяет связи по описанию схемы и строит
один план запроса, избавляя приложение от отдельного запроса на каждую строку.
Пути доступны в фильтрах, группировках, сортировке и агрегатных выражениях;
`EXPLAIN ANALYZE` показывает выбранный способ выполнения.

Навигация работает для чтения. Она проходит по одноколоночным внешним ключам
к PRIMARY KEY или UNIQUE NOT NULL в пределах одной базы, до восьми переходов.
Изменения выполняются с явным указанием таблицы; для обратного перехода
«один ко многим» используются обычные JOIN.
Подробнее — в [руководстве по навигационным ссылкам](doc/src/content/docs/ru/sql/navigable-references.md).

### Встроенная ORM

В состав RadixDB входит ORM для построения запросов и работы с записями
из Rust. Она интегрирована во встраиваемый API базы и TCP-клиент.
Операции ORM преобразуются в обычный SQL с типизированными параметрами:
запросы ORM и SQL могут использовать одно соединение, одну транзакцию
и один снимок данных.

```rust
use radixdb_orm::{table, Expr, OrmBuilder, QueryBuilder};

let query = QueryBuilder::from_relation(table("employees"))
    .select([
        Expr::column("name"),
        Expr::navigation("employees", ["department_id", "name"]),
    ])
    .filter(Expr::column("department_id").eq(10))
    .limit(100);

let compiled = query.to_sql()?;
```

Этот пример строит запрос без открытия соединения. Значение фильтра становится
параметром, а не вставляется в текст SQL. Подключённое приложение может
выполнить построенный запрос через клиент или ORM-интерфейс встроенной базы.

ORM поддерживает два способа работы с данными. Сгенерированные Rust-модели
предоставляют типизированные колонки, ключи, ссылки и отслеживание изменений.
Динамические сущности используют описание схемы во время выполнения:
это удобно для средств администрирования и приложений с изменяемой структурой
данных. Описание схемы можно экспортировать для автономной генерации моделей.

Запросы поддерживают соединения, навигацию, группировки, оконные функции,
CTE и подзапросы. Конструкторы DDL описывают таблицы и ограничения.
Операции с записями различают пропущенное значение, NULL и присвоенное значение.
Версионированное JSON-представление и описания форм позволяют строить
инструменты просмотра и редактирования запросов и данных.

`Reference<T>` хранит ключ связанной записи и поддерживает явную навигацию
для чтения. Сохранение записи не запускает скрытую загрузку или сохранение
всего графа связанных объектов. Автоматические миграции схемы решаются отдельно.
См. [руководство ORM](doc/src/content/docs/ru/clients/orm.md) и
[готовый пример на Rust](examples/public/rust-orm/).

### Trusted native extensions

RadixDB 1.2 предоставляет stable C ABI, безопасный Rust SDK и deterministic
package tooling для operator-trusted native extensions. Extension может
добавлять bounded scalar types, native scalar и batch functions, binary
operators, B-tree/hash/bitmap operator classes и bounded planner support.
Proving extension `radixdb-spatial` реализует geometry values, predicates и
Morton-key B-tree access целиком через эту public boundary.

База сохраняет владение storage, WAL, MVCC, catalog publication, index pages,
ACL и recovery. Native packages работают in-process и потому считаются
доверенными наравне с server binary; startup loader принимает только полные,
проверенные по checksum packages из exact absolute allowlist entries. Database
bindings закрепляют package version, fingerprint и codec identity.

Эта extension surface вместе с functions, procedures и triggers образует
практический базовый набор для предметного поведения базы. Более сложные
сценарии можно собирать из этих механизмов, даже если соответствующий синтаксис
или порядок работы отличается от PostgreSQL. См.
[эксплуатацию extensions](doc/src/content/docs/ru/administration/extensions.md),
[руководство разработчика](doc/src/content/docs/ru/programming/native-extensions.md)
и [публичный пример Rust](examples/public/rust-plugin/).

### Возможности SQL

- Транзакции MVCC, SQL DDL/DML, соединения, подзапросы и оконные функции.
- Индексы B-tree, hash, bitmap и HNSW, включая уникальные и частичные.
- Значения UUID, генерация UUIDv7 и реляционные ограничения.
- `ROLLUP`, `CUBE`, `GROUPING SETS` и `GROUPING()`.
- Навигация по ссылкам, например `employee.department_id.name`.
- Trusted native extensions с external scalar types, functions, operators и
  planner-aware index classes.

[Матрица возможностей SQL](doc/src/content/docs/ru/appendices/compatibility.md) описывает
собственный поддерживаемый синтаксис и ограничения RadixDB. Сетевой протокол
и SQL-диалект принадлежат RadixDB; drop-in-совместимость с PostgreSQL не
является целью проекта.

### PL/SQL: прикладная логика внутри базы

Разрабатываемая RadixDB 1.2 включает собственный процедурный SQL-язык. Функции, процедуры и
триггеры позволяют размещать проверки, многошаговые изменения и бизнес-правила
рядом с данными, в одной транзакции с контролируемыми операциями.

Принятая реализация содержит типизированные переменные и аргументы, условия,
циклы, курсоры, обработку исключений, параметризованный динамический SQL,
хранимые функции и атомарные вызовы процедур через `CALL`. Триггеры
BEFORE/AFTER для строк и операторов используют типизированные записи `OLD` и
`NEW`. Выполнение разделяет транзакцию и ограниченную модель ресурсов с
SQL-движком; ошибка откатывает изменения внешнего оператора, включая эффекты
триггеров. Долговечные определения Jobs, записи попыток и штатный фоновый
scheduler входят в движок. Доставка выполняется как at-least-once; при риске
дублирования Procedure может использовать стабильный idempotency key попытки.

Это собственный PL/SQL RadixDB, а не слой совместимости с Oracle PL/SQL или
PostgreSQL PL/pgSQL.

### ACL: роли и управление доступом

Разрабатываемая RadixDB 1.2 включает проверяемые базой principals, roles и membership,
владение объектами, доступ к таблицам и столбцам, а также права `SELECT`,
`INSERT`, `UPDATE`, `DELETE` и `EXECUTE`. Подпрограммы выполняются с authority
вызывающего или владельца, а проверки происходят внутри движка. Выдача и отзыв
прав являются транзакционными изменениями каталога; последующее выполнение
учитывает новое состояние авторизации.

Row-level security не реализована. Штатный TCP-сервер аутентифицирует catalog
Principal по паролю и поддерживает обычный TCP в доверенной сети либо direct
TLS с проверкой сертификата и имени сервера. После входа движок применяет к
Principal права базы, схемы, объектов и подпрограмм.

### Начало работы

Используйте версию Rust из [rust-toolchain.toml](rust-toolchain.toml):

```bash
cargo build --locked --release --bin radixdb-server --bin radixdb-password --bin radixdb-cli --bin radixdb-smoke-client --features cli
target/release/radixdb-cli -e "SELECT 1"
```

CLI открывает локальные базы. Для постоянной базы укажите
`-d file:///path/to/database`; для подключения по TCP используйте Rust-клиент.
См. [установку сервера](doc/src/content/docs/ru/administration/installation.md),
[конфигурацию](doc/src/content/docs/ru/administration/configuration.md) и
[учебную базу RadixTrade](examples/public/radixtrade/).

Для обычного доступа приложения создайте catalog Principal с паролем. Для
административного доступа настройте Argon2id verifier, созданный утилитой
`radixdb-password`: после этого исходный пароль обязателен на каждом endpoint,
а беспарольный вход `root` отключён. Без verifier беспарольный `root` остаётся
только восстановительным входом через plaintext loopback endpoint. Перед
предоставлением доступа прочитайте [руководство по аутентификации](doc/src/content/docs/ru/administration/authentication.md)
и [политику безопасности](SECURITY.ru.md).
